## Architecture Summary

Open Brain is a **single-user, single-network modular monolith** implemented as a TypeScript + Python polyglot monorepo (pnpm workspaces, 8 packages + Python sidecars) fronting a Postgres-16 + pgvector knowledge store. Processing uses an **async event-driven pipeline** (BullMQ + Redis) with a DAG-structured FlowProducer topology for ingestion and ~19 scheduled repeatable jobs for skills/maintenance. The primary architectural spine is a **cost-tiered LLM gateway** (`LLMGatewayService` in `@open-brain/shared`) that routes tasks via `config/ai-routing.yaml` across five tiers (Ollama T0 → Jetson T1 → Spark T1 → Haiku T1 → Sonnet T2) with bounded fallback and per-tier cached SDK clients. All external access is fronted by a Cloudflare Tunnel; internal Docker services share one bridge network (`open-brain`) with no mTLS / service identity, relying on network isolation.

## Design Decision Log

### Decision: Modular monolith over microservices
- **What it solves:** Single operator needs one deployable unit on an Unraid box with a hard-cap on processes.
- **What was chosen:** One monorepo (pnpm), one shared package with the schema + gateway + logger, Docker Compose with 13 services built from the same `Dockerfile` via target-stage pattern for TS services + separate Python sidecar images.
- **Likely rejected alternatives:** Microservices with independent deploys (rejected — operational burden for 1 user), Nx/Turborepo (tsup + pnpm is sufficient), single container (rejected — can't bound Whisper/Postgres memory separately).
- **Assessment:** Sound.
- **Rationale:** The blast radius and refactor surface is acceptable; `@open-brain/shared` as the single source of truth for logger, LLM clients, LLM gateway, Drizzle schema, prompt templates, budget tracking is well-executed and has visibly reduced duplication (D7 Phase 7).

### Decision: Postgres + pgvector (no Supabase, no Qdrant)
- **What it solves:** Single store for relational, FTS, and ANN search.
- **What was chosen:** `pgvector/pgvector:pg16` base image, HNSW index, `vector(768)` everywhere, hybrid search via a dedicated SQL function (`hybrid_search`, `fts_only_search`) with RRF inside SQL — not JS.
- **Likely rejected alternatives:** Qdrant / Milvus (deferred per D67 until >100K embeddings; current ~11K–15K captures), Supabase (rejected — explicit design principle "infrastructure you own"), Elasticsearch (operational weight, no vector parity with pgvector).
- **Assessment:** Sound for current scale. Concern: `hybrid_search` and `actr_temporal_score` are PL/pgSQL; the temporal decay logic is **duplicated** in TS (`applyTemporalDecay` in `search.ts`) — two code paths to keep in sync. See M-4.
- **Rationale:** Right scale match; clean migration path when volume warrants Qdrant; pgvector HNSW handles ~100K gracefully.

### Decision: BullMQ + Redis with FlowProducer DAG
- **What it solves:** Async, observable, retryable processing with explicit dependency ordering for ingest stages.
- **What was chosen:** `ingest-pipeline.ts` builds a FlowJob tree: `ingest-root` parent runs LAST after `embed-capture` (critical, `failParentOnFailure: true`) + `extract-entities` (non-critical, `removeDependencyOnFailure`) + optional `wiki-ingest`. Inside `ingest-root`, `link-entities` runs inline then `check-triggers` is enqueued.
- **Likely rejected alternatives:** Linear chain (older code path; kept behind `PIPELINE_USE_FLOWS=true` now always-on — see L-1), Temporal / Inngest (overkill), Postgres LISTEN/NOTIFY-only (used elsewhere for SSE but not resilient enough for retries).
- **Assessment:** Sound. The critical/non-critical distinction (embed failure blocks, entity extraction failure doesn't) matches product intent.
- **Rationale:** Good fit. One concern: DAG structure is documented in the code comment block rather than a separate diagram; evolving the topology (e.g. adding a "classify" stage as a hard gate) will require care. See M-2.

### Decision: Task-based tier routing via `ai-routing.yaml`
- **What it solves:** Minimize paid API spend; route simple classification to free local/remote GPU endpoints and reserve paid tiers for synthesis/governance.
- **What was chosen:** `task_routing` map (task_name → tier_key) + `model_tiers` map (tier_key → provider + model + base_url + costs + `fallback: next_tier`). Gateway resolves per call, caches per-tier OpenAI SDK clients, executes with bounded fallback (MAX_FALLBACK_HOPS=2 + 3-retry same-tier window for "Loading model" 503s).
- **Likely rejected alternatives:** Hardcoded routing in services (fragile — D74/D77 cost incident was caused exactly by a hardcoded path that bypassed tier), generic "alias" model names without tier intent (rejected — no audit trail, no fallback).
- **Assessment:** Sound with caveats. The regression from D74 (cost fields zeroed out) was severe: **a config-only data error caused $100+ Anthropic overage**. Structural mitigations: CLAUDE.md rule "verify ai-routing.yaml cost path before ANY bulk operation" is human-dependent; there is no **startup validation** that every tier has non-null costs. See H-1.

### Decision: Embedded MCP server at `/mcp` (not a separate container)
- **What it solves:** Stateless Streamable HTTP transport with minimal deployment surface; all DB-reading tools share the same connection pool and service instances as core-api.
- **What was chosen:** Per-request `McpServer` + `WebStandardStreamableHTTPServerTransport` created in `app.all('/mcp')` handler; stateless mode (no session IDs). 8 tools + 1 resource registered per request.
- **Likely rejected alternatives:** Separate container with its own DB pool (duplication), long-lived server with stateful sessions (stateless is correct for idempotent tools), MCP over SSE only (compatibility concerns — Streamable HTTP is the newer standard).
- **Assessment:** Sound.
- **Rationale:** Correct choice for Hono/Workers runtime style; stateless matches single-user pattern. Client_id derivation from token hash is a clever way to get per-client activity logs without needing a client registry.

### Decision: Hono + Drizzle (not Express + Prisma)
- **What it solves:** Type-safe API + ORM with excellent TypeScript ergonomics.
- **What was chosen:** Hono routes (lightweight, web-standard Request/Response), Drizzle schema + drizzle-kit migrations (`packages/shared/drizzle/0000-0022`).
- **Likely rejected alternatives:** Express (heavier, no native web-standards), Prisma (less pgvector control — raw SQL needed for `hybrid_search` anyway).
- **Assessment:** Sound. Drizzle's type safety has paid off (e.g. the `captures.source` CHECK constraint work in PR #101 leveraged schema + TS union together).

### Decision: Hebbian + spreading activation + memory consolidation (cognitive memory)
- **What it solves:** Search quality compounds over time as access patterns form; near-duplicates get merged automatically on a Sunday cron.
- **What was chosen:** `capture_associations` table (canonical `a < b` pair ordering), weight decay `count * exp(-0.005 * hours)`, pruning below 0.1, top-10 co-access pairs only (D26). Spreading activation via `spreading_activation` SQL function; 2 hops, fan-out 10. Memory consolidation: cosine > 0.92, min cluster 3, top 5/run, 4 AM Sundays.
- **Likely rejected alternatives:** All-pairs co-access (N² blowup), no decay (stale associations dominate), synchronous graph traversal in app code (rejected — SQL function is faster and within DB).
- **Assessment:** Sound but under-monitored. Consolidation runs weekly with soft-delete — recoverable — but there's **no dashboard panel measuring merge quality**, so a regression in prompt quality could silently degrade captures. See M-6.

## Architecture Pattern Assessment

- **Pattern identified:** Modular monolith + event-driven processing + external LLM gateway aggregator. Strongly influenced by **twelve-factor** principles (config in env, processes as disposable, port binding, stateless web process). Domain pattern: **cognitive memory model** (Hebbian associations, spreading activation, consolidation) layered on top of a knowledge base.
- **Fit score:** 5 for current requirements; 3.5 for "evolve into a 3-user / home-family system" if ever desired.
- **Rationale:** Single-user, single-operator, self-hosted with a tight cost cap and a hardware ceiling — this is almost a textbook fit for a modular monolith. The seams are in the right places: BullMQ for async, gateway for routing, config for policy, Drizzle for schema. The only architecturally "serious" cost-of-change risk is the duplication of scoring logic between SQL (`actr_temporal_score`) and TypeScript (`applyTemporalDecay`).
- **Specific concerns:**
  - The **batch-ingest sidecar + host cron** design is pragmatic but operationally split-brain: the TS workers process real-time captures and the Python sidecars process batch email/financial/utility data. They meet at the captures API boundary. This duplicates some concerns (dedup, rate limiting, retry). Documented in CLAUDE.md's "two-track pipeline" — intentional and sound. Watch for drift as Python sidecars gain more skills.
  - The **five-tier LLM routing** is a conceptual win, but the fallback chain discipline ("same-provider only for agent loops" per `AgentClientResolution`) is a correctness gate that lives in code comments + tests, not in types. Could be made a type-level constraint.

## Evolution Assessment

**Runway:** 1–2 years of plausible new features without structural rewrite, assuming (a) capture volume stays under ~100K, (b) single-user remains the mode, and (c) the cost-tiered routing discipline holds. The architecture has **explicit evolution hinges** already in place:
- Qdrant migration plan if embeddings pass 100K (D67)
- `ingest-routes.yaml` for declarative capture → pipeline mapping (not yet fully used)
- `BaseSkill` abstraction has absorbed 27 skills cleanly — new skills are cheap
- `openai_compat` provider has absorbed 3 different local/remote GPU endpoints (Ollama, Jetson llama.cpp, Spark vLLM) without code changes per endpoint — future endpoints (Groq, Fireworks, Together) are a YAML edit

**First design elements to become constraints:**
1. **`config/ai-routing.yaml` as the single source of cost truth** (C-1 / H-1 finding). If this gets out of sync (or a tier is ever added without cost fields), the budget breaker silently disengages. This has already happened once (D74); the structural fix is type-level validation.
2. **The Python-sidecar ↔ TS-workers boundary** will strain as more batch pipelines are added (next candidates: iCal, URL capture, Notion mirror). The current pattern is "host cron + `docker exec`" which works but is opaque from BullMQ's point of view. At 3+ sidecars, consider a unified sidecar scheduler or migrate the Python pipelines to BullMQ-triggered jobs running in a python-worker container.
3. **The search pipeline's scoring** (FTS rank + vector + RRF + ACT-R decay + Hebbian boost + spreading activation) is now a **6-factor composition** with each factor's weight either hardcoded or implicit. Tuning will get hard; consider exposing a "retrieval profile" concept (e.g., "precision", "recall", "recent", "exploratory") that preselects factor weights.
4. **The cognitive memory layer** (Hebbian + consolidation) currently has no human-in-the-loop feedback except implicitly through search-rank improvement. Without a review UI for merge decisions, quality can degrade silently. This will become a drag on trust as consolidations accumulate.
5. **The web package ↔ shared package type drift-guard** (PR #97) covers `IngestSourceType` and `FileUploadStatus` but NOT `CaptureSource` — which just regressed (PR #101 discovered a 9th value). Extending drift-guard to cover all TS unions that web consumes is the right next step.
